# Verificação proporcional ao redesign

## Documentação

Se mudar apenas Markdown: conferir links/caminhos, coerência, tamanho e diff. Não iniciar servidores, fazer capturas ou executar build só por isso.

## Código visual

1. Conferir diff e preservar funcionalidades, dados, contratos e permissões.
2. Executar lint. Executar verificação de tipos para mudanças TS/TSX e build quando alterar integração, estilos compilados ou componentes que afetem a entrega. Depois de passar, não repetir sem nova alteração relevante ou falha.
3. Inspecionar a tela afetada em desktop e mobile e nos dois temas. Mudança de layout compartilhado exige 360, 390, 768, 1024 e 1440 px; corrigir overflow e conteúdo cortado.
4. Verificar teclado, foco visível, labels, Escape, contenção/retorno de foco, alvos de toque e redução de movimento. Conferir contraste; não usar só cor para status.
5. Exercitar o fluxo alterado: carregamento, vazio, erro, reenvio e sucesso. Preservar dados após falha e prevenir duplicidade durante envio.
6. Salvar capturas representativas e registrar no STATUS o que foi efetivamente verificado e o que ficou pendente.

Preservar testes existentes e verificar regressões dos consumidores quando mudar componentes compartilhados. Não criar testes que apenas repitam detalhes de estilo nem executar toda a suíte do backend sem relação com a alteração.

## Ambiente

`services/api.js` aponta para a API publicada como fallback. Usar fixtures locais ou ambiente de testes configurado explicitamente para navegação que possa gravar dados. Nunca validar aparência com pagamentos ou cadastros reais. Não alterar `.env`, credenciais ou o ambiente publicado como parte do redesign.

O primeiro incremento foi validado com navegador/locators disponíveis, sem instalar Playwright CLI e sem suíte E2E integrada. Não afirmar cobertura automática inexistente. Se uma ferramenta estiver indisponível, registrar o limite e validar o que for possível com as ferramentas existentes.
